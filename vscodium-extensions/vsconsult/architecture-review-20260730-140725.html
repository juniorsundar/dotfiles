1 · Split the PickerHost: put the picker session behind a message seam

Strong

Files

src/host/host.ts (710 LOC — 41% of all implementation), src/host/protocol.ts, src/host/lifecycle.ts, src/host/virtualPreview.ts, src/host/debounce.ts

Problem

The host fuses three concerns in one module: the session state machine (source streaming, abort guards, narrowing dispatch, preview scheduling), the vscode adapters (buildPickerContext, focus commands, reveal), and the shared view HTML (~200 LOC of template string with inline JS). The last two bug fixes — preview bloat, focus timing — landed in the state-machine part, which is only reachable in tests by mocking the entire vscode module and simulating webview messages. The interface is narrow (start / resolveWebviewView / dispose) but the interesting behaviour sits behind the wrong seam: the test surface is vscode, not the session.

Solution

Extract a PickerSession module whose whole interface is messages in, messages out: start(picker) → OutboundMessage[], handle(InboundMessage) → OutboundMessage[], cancel(). It owns candidates, query, the abort guard, stream consumption, and debounce timing — all pure of vscode. The remaining host becomes a thin adapter: webview events → session, session messages → webview.postMessage, plus the vscode-backed picker context helpers. Move the view HTML into its own host-owned module (ADR-0002 keeps it host-owned and static; it need not live in the same file).

Benefits

Locality: the race-prone logic lives in one module you can read top to bottom. Leverage: every future picker type exercises the same session through two functions. Tests: the preview-bloat and focus-timing regressions become plain message-sequence tests — no vscode mock scaffold, no fake webview. The existing host.test.ts mock boilerplate mostly evaporates.

2 · Delete matcher.ts — a dead shallow duplicate of the file picker's Narrowing

Strong

Files

src/matcher.ts (52 LOC) · src/matcher.test.ts · superseded by src/filePicker/narrow.ts

Problem

matcher.ts is a leftover from before the picker-core extraction (ticket 3). Nothing imports it — zero inbound edges outside its own test. It re-implements what filePicker/narrow.ts now owns: the identical isPathBoundary check and the identical scoreText options (end-weighting + length penalty). Its passing test suite is false confidence — it tests code no picker runs.

Solution

Delete matcher.ts and matcher.test.ts. The deletion test passes in its strongest form: the complexity doesn't move — it simply ceases to exist, because the behaviour is already owned by the file picker's Narrowing part, which is tested through narrow.test.ts.

Benefits

Locality: one place owns path-biased narrowing — today a reader must diff two files to learn which is live. Leverage: none lost; the live seam (fuzzy.ts per ADR-0001) is untouched. Tests: suite shrinks to tests that guard shipping behaviour.

3 · Co-locate the file picker's five parts in one module

Worth exploring

Files

src/filePicker/{index,source,narrow,render,accept,preview}.ts — six files, ~170 LOC total, one export each

Problem

Understanding the file picker means bouncing across six files averaging under 30 LOC. The five-part bundle (Source, Candidate, Narrowing, Render, Accept) is the right interface — spec 0001 defines it — but the one-file-per-part layout is a hypothetical seam: only one picker type exists, so nothing yet varies across the file boundaries. Deletion test on, say, render.ts (14 LOC): deleting it concentrates complexity into the picker module without loss. Note preview.ts (19 LOC) is also the only picker part with no test.

Solution

Keep the Picker interface exactly as registered with the host; move the five parts of the file picker into a single filePicker.ts module whose only export is createFilePicker(env, registry). The parts become internal functions — an internal seam, private to the module, still exercised by the existing tests through the Picker bundle.

Benefits

Locality: one picker type = one readable file; the domain language (Source / Narrowing / Render / Accept) survives as section structure. Leverage: adding the grep picker still costs one new module. Tests: unchanged surface — tests already go through the parts' public signatures. Counter-argument worth weighing: the current layout pre-figures the grep picker and mirrors CONTEXT.md one-to-one; this may be cheap structure to keep.

4 · Concentrate the three hand-rolled vscode adapters into one environment module

Worth exploring

Files

src/extension.ts (workspace/file adapters) · src/host/host.ts buildPickerContext (document/preview adapters, ~100 LOC inline) · src/host/lifecycle.ts HostEnv

Problem

Knowledge of the vscode API is scattered across three ad-hoc adapter shapes, each invented locally: the FileSourcingWorkspace literal in extension.ts, the picker-context helpers built inside the host, and HostEnv for lifecycle. Each has its own fake in its own test file. Nothing contradicts an ADR — but the extension↔vscode seam is currently three seams, none of them named in CONTEXT.md.

Solution

One vscodeEnv module owns every touch of the vscode API: workspace files, documents, commands, window/origin state. extension.ts, the host, and lifecycle all accept it. Pickers still see only the narrow picker context — the env module is what the host builds that context from.

Benefits

Locality: one file answers "how does this extension talk to vscode." Leverage: one fake env serves every test, replacing per-test mock scaffolds. Naturally pairs with candidate 1 — the host split is what makes the env seam clean. Weaker standalone; do them together or skip this one.

Top recommendation

Tackle candidate 1 first — split the PickerHost so the picker session sits behind a message seam. It is the largest module (41% of the implementation), it is where the last two bugs actually lived, and it is the only place where testing requires mocking the entire vscode API. Deepening it converts your most bug-prone territory into your most testable module, and it unlocks candidate 4's env seam for free.

Candidate 2 is a free win — deleting matcher.ts takes minutes and removes the only outright dead code. Do it in the same pass.

Candidates 3 and 4 are worth a conversation, not a commitment: both trade the current forward-looking structure (one file per picker part, adapters colocated with their consumers) against today's single-picker reality.
