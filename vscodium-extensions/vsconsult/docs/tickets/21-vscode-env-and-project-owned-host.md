# 21 — vscodeEnv capabilities; project-owned PickerHost; thin extension wiring

**What to build:** Centralize direct VS Code integration behind one vscodeEnv module and reduce PickerHost to a project-owned controller, leaving the extension entrypoint as a thin composition root. vscodeEnv constructs focused capability interfaces — workspace sourcing, documents and virtual preview, commands and focus, Lifecycle, configuration, and Shared-view registration/transport. Consumers receive only the capabilities they use; there is no broad environment object passed through the application as a service locator. Direct imports of the VS Code package are restricted to vscodeEnv and the extension entrypoint; PickerHost, PickerSession, the Shared view adapter, Lifecycle orchestration, and preview-content policy use project-owned types and injected capabilities. PickerHost becomes a project-owned controller adapted to VS Code provider registration at the entrypoint rather than implementing WebviewViewProvider itself; its responsibilities are resolving/attaching a Shared view adapter, starting a Picker by registered id, coordinating inputs and outputs, executing effects, owning Host interaction and Return context, running Lifecycle, applying the injected default-Picker policy, and disposal. The extension entrypoint builds production capabilities, assembles picker factories and the Registry, adapts PickerHost to provider registration, registers commands, and wires the injected default Picker id. Existing virtual preview behavior remains session-bounded with one stable virtual document; the bounded-content and editor-history policy from the preview ADR is unchanged. An architectural check verifies that direct VS Code imports exist only in vscodeEnv and the extension entrypoint. User-visible behavior is unchanged across the whole refactor.
